# Verifying the headless image

How someone who has the container image and nothing else from this project checks who built it,
from which commit, and what it contains. The checks need three programs, `cosign`, `jq` and
`sha256sum`, and no network: they run against an OCI image layout on disk, so a disconnected site
verifies exactly what a connected one does.

## What this is not

**A signature is evidence, not an authorization.** It says this project's key signed statements
about these exact bytes; it decides nothing about whether they may run in your environment. That
decision is yours and your authorizing official's. Nothing on this page is an authority to
operate, a compliance determination, or a claim that the image is free of vulnerabilities; the
image's scan and its STIG applicability statement are in `headless-image.md`.

## What is attached to each published image

The publishing job (`.github/workflows/headless-image.yml`, job `publish`) pushes the image by
digest and attaches four statements, each signed with the project's held key and stored in the
registry as an OCI referrer of the image's digest (`scripts/image_supply_chain.sh`):

| Statement | Predicate type | What it says |
|---|---|---|
| Signature | `https://sigstore.dev/cosign/sign/v1` | the key holder signed this digest |
| Build provenance | `https://slsa.dev/provenance/v1` | the builder, the source repository, the exact commit, and every other input by digest (`mix trinity.image.provenance`) |
| SBOM | `https://cyclonedx.org/bom` | the tree's CycloneDX bill for that commit (`mix trinity.sbom`), unchanged |
| AI-BOM | `https://github.com/ScriptKittyOS/Trinity/blob/main/docs/regulated/image-verify.md#ai-bom` | a CycloneDX ML-BOM of the models the image carries (`mix trinity.image.aibom`) |

The image also names its commit in its own configuration, as the label
`org.opencontainers.image.revision`. The build applies it only when no tracked file differed from
that commit, and the provenance is refused for an image without it.

Beside these, the job asks GitHub for its own build provenance for the same digest, signed through
the workflow's identity and recorded in the public Sigstore log, which a connected consumer can
check with `gh attestation verify oci://IMAGE@DIGEST --repo ScriptKittyOS/Trinity`.

**Status: the publishing job has not run yet.** It waits on two things: the project's signing key
(below), and the image's own checks passing, because nothing is published while they fail. Until
then no published image exists to verify, and the sequence below has been run against images
signed with keys made for the test.

### Build provenance and SLSA: the level claimed, and why

**Claimed: SLSA Build L1** for the provenance you verify with the project's public key. It exists,
is signed, and names the builder, the repository and the commit, which is what L1 asks for. It is
**not L2**, because L2 requires the build platform itself to generate and sign the provenance, and
this provenance is generated by a step of the build job and signed with a key that job can read: a
compromised build step could write a false one. GitHub's own provenance beside it is generated and
signed by the platform, which GitHub documents as Build L2; the claim will move to L2 when a run of
the publishing job has verified it, and not before. Neither path is L3, which needs the provenance
made in isolation from the build's own steps.

The claim lives in `ci/headless/slsa.yaml`, and `mix trinity.image.slsa` fails the quality gate if
it is raised above what the workflow's mechanism supports, or to L2 or more without a run that
verified.

### The signing key, and why there is no public transparency log

The image is signed with a **held key** (ECDSA P-256, cosign's format), not keylessly through a
public transparency log. The reason is the deployment this matters most for: a disconnected or
classified site cannot reach a public log, and a keyless signature needs one at signing time and a
copy of the log's trusted root, kept current, at verification time. With a held key the public key
is all a verifier needs, connected or not, and a site that re-signs images inside its own boundary
can use the same method with its own key.

What that costs, stated rather than left to be discovered:

* **A stolen key signs silently.** No log records each signature, so misuse is not visible to
  anyone. The key is held only by the publishing job, in the repository's secrets or an HSM.
  A connected consumer can also require GitHub's logged provenance, which a thief holding only the
  key cannot produce; a disconnected consumer has the key signature alone, and that is the
  residual risk.
* **Rotation and revocation are out of band.** A new key is a new public key in this repository,
  announced in the changelog; there is no log to revoke against.

**The project's public key is not in the tree yet.** It will be `ci/headless/cosign.pub`, committed
by the maintainers when the key is generated, and the publishing job refuses to sign with a key
whose public half differs from that file.

### What crosses to whom when an image is published

| Destination | What is sent | Raw or hashed |
|---|---|---|
| The repository's container registry (`ghcr.io`) | the image, the four signed statements above | raw: they are what is published |
| GitHub's attestation store and the public Sigstore log | GitHub's provenance: the repository, the workflow, the commit, the image digest | raw: public by design |
| Anything else | nothing; the held-key signatures are not uploaded to any log | |

## Verifying

### Get the image as a layout

From a registry you can reach, by digest, never by tag:

```
cosign save --dir trinity-layout ghcr.io/scriptkittyos/trinity-headless@sha256:<digest>
```

The directory carries the image, its four statements, and nothing else, and can be carried into a
disconnected site as it is. Verify it there, then load it into your registry by digest.

### The sequence

Set the inputs, then run the block below in `bash`. The block is the test:
`test/image_supply_chain_test.exs` and the publishing job both extract this exact text from this
file and run it, so it cannot drift from what works.

| Variable | What it is |
|---|---|
| `LAYOUT` | the directory `cosign save` wrote |
| `PUBKEY` | the project's public key file |
| `COMMIT` | the full commit you expect the image to come from (a release tag's commit) |
| `REPOSITORY` | `https://github.com/ScriptKittyOS/Trinity` |
| `BUILDER` | `https://github.com/ScriptKittyOS/Trinity/.github/workflows/headless-image.yml@<ref>`, the workflow at the ref that built it |
| `REFERENCE_SBOM` | optional: the bill you generated yourself from `COMMIT` (`git checkout COMMIT && mix deps.get && mix trinity.sbom`) |
| `COSIGN` | optional: the cosign program, default `cosign` |

Each step prints `OK` and what it established, or `FAIL` with the reason and exits with its own
status: 10 the layout, 11 the signature, 12 the provenance's signature, 13 the commit, 14 the
builder or repository, 15 the SBOM's signature, 16 the SBOM's contents, 17 the AI-BOM.

<!-- verify:begin -->
```bash
set -euo pipefail
: "${LAYOUT:?}" "${PUBKEY:?}" "${COMMIT:?}" "${REPOSITORY:?}" "${BUILDER:?}"
COSIGN="${COSIGN:-cosign}"
AIBOM_TYPE="https://github.com/ScriptKittyOS/Trinity/blob/main/docs/regulated/image-verify.md#ai-bom"
WORK=$(mktemp -d)
trap 'rm -rf "$WORK"' EXIT
fail() { echo "FAIL $1: $2" >&2; exit "$3"; }
ok() { echo "OK $1: $2"; }
blob() { echo "$LAYOUT/blobs/sha256/${1#sha256:}"; }
offline=(--key "$PUBKEY" --offline --insecure-ignore-tlog=true --local-image)

# 1. The layout: every blob is the bytes its name says, and the image's blobs are all present.
#    cosign checks the manifest's digest, not the layers it lists, so this step is not optional.
(cd "$LAYOUT/blobs/sha256" && for f in *; do printf '%s  %s\n' "$f" "$f"; done |
  sha256sum --quiet --check - >"$WORK/blobs.txt" 2>&1) ||
  fail layout "a blob does not match its digest: $(head -1 "$WORK/blobs.txt")" 10
[ "$(jq '.manifests | length' "$LAYOUT/index.json")" = 1 ] ||
  fail layout "index.json must name exactly one image" 10
DIGEST=$(jq -r '.manifests[0].digest' "$LAYOUT/index.json")
[ -f "$(blob "$DIGEST")" ] || fail layout "the image manifest $DIGEST is missing" 10
for d in $(jq -r '.config.digest, .layers[].digest' "$(blob "$DIGEST")"); do
  [ -f "$(blob "$d")" ] || fail layout "the image's blob $d is missing" 10
done
ok layout "every blob matches its digest; the image is $DIGEST"

# 2. The signature: a statement signed by the key names this digest.
"$COSIGN" verify "${offline[@]}" "$LAYOUT" >"$WORK/signature.json" 2>"$WORK/err" ||
  fail signature "$(tail -1 "$WORK/err")" 11
ok signature "signed by the key in $PUBKEY"

# Each attestation of a type, as the statements cosign verified, one JSON array.
statements() {
  "$COSIGN" verify-attestation "${offline[@]}" --type "$1" "$LAYOUT" >"$WORK/att.jsonl" 2>"$WORK/err" ||
    return 1
  jq -s '[.[] | .payload | @base64d | fromjson]' "$WORK/att.jsonl" >"$2"
  jq -e --arg d "${DIGEST#sha256:}" 'length > 0 and all(.[]; [.subject[].digest.sha256] == [$d])' "$2" >/dev/null
}

# 3. The provenance: signed by the key, naming the commit, the builder and the repository.
statements slsaprovenance1 "$WORK/provenance.json" ||
  fail provenance "no provenance for $DIGEST signed by the key: $(tail -1 "$WORK/err")" 12
CONFIG=$(jq -r '.config.digest' "$(blob "$DIGEST")")
LABEL=$(jq -r '.config.Labels["org.opencontainers.image.revision"] // ""' "$(blob "$CONFIG")")
[ "$LABEL" = "$COMMIT" ] ||
  fail commit "the image says it was built from '$LABEL', not $COMMIT" 13
jq -e --arg c "$COMMIT" 'all(.[]; [.predicate.buildDefinition.resolvedDependencies[]
    | select(.uri | startswith("git+")) | .digest.gitCommit] == [$c])' \
  "$WORK/provenance.json" >/dev/null ||
  fail commit "the provenance names another commit than $COMMIT" 13
ok commit "the image and its provenance both name $COMMIT"
jq -e --arg b "$BUILDER" --arg r "$REPOSITORY" 'all(.[]; .predicate.runDetails.builder.id == $b
    and .predicate.buildDefinition.externalParameters.repository == $r)' \
  "$WORK/provenance.json" >/dev/null ||
  fail builder "the provenance names another builder or repository than $BUILDER, $REPOSITORY" 14
ok builder "built by $BUILDER from $REPOSITORY"

# 4. The SBOM: signed by the key, and, given your own bill for the commit, the same components.
statements cyclonedx "$WORK/sbom.json" ||
  fail sbom "no SBOM for $DIGEST signed by the key: $(tail -1 "$WORK/err")" 15
ok sbom "$(jq '.[0].predicate.components | length' "$WORK/sbom.json") components, signed by the key"
components='[.components[]? | {group, name, version, purl, hashes}] | sort_by(.purl // "", .name)'
if [ -n "${REFERENCE_SBOM:-}" ]; then
  jq "$components" "$REFERENCE_SBOM" >"$WORK/want.json"
  jq ".[0].predicate | $components" "$WORK/sbom.json" >"$WORK/got.json"
  diff "$WORK/want.json" "$WORK/got.json" >"$WORK/sbom.diff" ||
    fail sbom-match "the attested SBOM differs from $REFERENCE_SBOM: $(grep -m1 '^[<>]' "$WORK/sbom.diff")" 16
  ok sbom-match "the same components as $REFERENCE_SBOM"
else
  echo "NOT CHECKED sbom-match: no REFERENCE_SBOM was given"
fi

# 5. The AI-BOM: signed by the key; every model has a weights hash if shipped, and its datasets.
statements "$AIBOM_TYPE" "$WORK/aibom.json" ||
  fail aibom "no AI-BOM for $DIGEST signed by the key: $(tail -1 "$WORK/err")" 17
jq -e 'all(.[0].predicate.components[]? | select(.type == "machine-learning-model");
    ((.modelCard.modelParameters.datasets // []) | length > 0)
    and (.scope == "optional" or any(.hashes[]?; .alg == "SHA-256")))' \
  "$WORK/aibom.json" >/dev/null ||
  fail aibom "a model in the AI-BOM has no dataset list, or is shipped without a weights hash" 17
ok aibom "$(jq '[.[0].predicate.components[]? | select(.type == "machine-learning-model")] | length' \
  "$WORK/aibom.json") model(s) listed, signed by the key"
```
<!-- verify:end -->

### What the steps do not establish

* **The SBOM is the tree's bill**: every Hex package `mix.lock` resolves, tools used only to build
  and test included. It does not list the operating system's packages or the Erlang runtime inside
  the image; the image scan in `headless-image.md` is the evidence for those.
* **Without `REFERENCE_SBOM`, step 4 checks the bill's signature only**, and says so. Whether it is
  the bill of that commit is what the comparison checks.
* **Step 5 is the shape a stranger can check with `jq`.** The full profile, every dataset's licence
  or quoted terms and the embedding space's identity, is `mix trinity.image.aibom --check`, which the
  publishing job runs before it attests the bill.
* **cosign's own success message** says the claims' existence in the transparency log "was verified
  offline". With `--insecure-ignore-tlog=true` and a held key there is no log entry; read the step
  above, not that line.

## Build type

<a id="build-type-v1"></a>
The provenance's `buildType` is this section's URI. A build of this type is
`scripts/headless_image.sh build` at the commit named in `resolvedDependencies`, building
`ci/ironbank/Dockerfile` with the build arguments in `ci/headless/bases.env` (both bases pinned by
digest) from a context in which every resource of `ci/ironbank/hardening_manifest.yaml` was checked
against its digest. `externalParameters` names the repository, the ref, the recipe and the bases
file; `resolvedDependencies` lists the commit, every resource and both bases by digest.

<a id="ai-bom"></a>
The AI-BOM's predicate type is this section's URI; the predicate is a CycloneDX 1.6 document whose
`metadata.properties` carry `trinity:bom-kind` = `ai-bom`. `ci/headless/ai_models.yaml` is its
source, and says why it lists no model today: no weights are baked into any image before legal
review of their licence and training-data terms.
