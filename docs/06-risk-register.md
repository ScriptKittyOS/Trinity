| R21 | **Answered 2026-09-24 for the receipt field set, which was the open half.** Slice 024 proposed the `signed_payload` field set for review and built "the default until cleared"; nothing cleared it until now, and slice 120's AC3 could not be met while that was true. Two questions, both now answered from published standards rather than from instinct. **Does the field set reproduce a third party's protected mechanism?** No, because it contains no mechanism anyone owns: `prev_hash` with `seq` is a forward-integrity hash chain (Bellare and Yee 1997; Schneier and Kelsey 1998), `key_id` is COSE `kid`, `scheme` occupies COSE `alg`'s role, `at` is RFC 3339, `subject` is in-toto's Statement subject, `chain_scope` is Certificate Transparency's per-log scoping, `fingerprint` is an RFC 8785 canonical-digest commitment and `decision` is XACML's PDP outcome. IETF **RFC 9943** (Standards Track, June 2026) standardises this whole object class as COSE_Sign1 Signed Statements and Receipts, which settles it: an open standard for the thing means the mechanism is nobody's to protect. **May policy identifiers enter `signed_payload`?** No, and the existing placement in unsigned `meta` is confirmed rather than merely tolerated. SLSA's attestation model separates `externalParameters` (untrusted, MUST be included and verified downstream) from `internalParameters` (platform-set, trusted, OPTIONAL, not verified downstream); a policy identifier is the second kind. Field-tier minimisation (arXiv 2608.25474) gives the governing property: the ledger commits to a canonical digest of the full parameters computed *before* minimisation, so "reclassifying a field changes what is disclosed without invalidating a historical entry, reopening a hash, or altering what an offline verifier checks" - Trinity already holds that commitment as the fingerprint, and moving policy identifiers into the signed bytes would convert a revisable disclosure decision into an immutable one for no gain, since a downstream verifier cannot evaluate Trinity's policy anyway and `decision.basis` already names the layer that decided inside the signed bytes. The original hazard also holds: if policy identifiers ever come from the external authority plane, embedding another party's namespace in immutable signed bytes is exactly what this row warns about, and in `meta` a namespace change is a metadata change rather than a scheme bump. **The rule, so this is not re-litigated:** the signed payload carries the commitment and the decision facts; anything platform-set, revisable or another party's namespace goes in `meta`. | R26 | Counter-example recorded 2026-09-24, in slice 090, and it corrects a heuristic the rows above state. At commit `b1bca1f` the `pull_request` run passed all four checks and the `push` run of the **same commit** failed `postgres` (runs 36001064067 and 36001057879). By the reading the 2026-09-23 entry offers - the code did not change between the green run and the red one, so the fault is the environment - this was R26 again. **It was not.** It was a real defect in slice 080's code, on a genuinely racy path: every call into a child session is a `gen_statem.call`, and a call into a process that dies exits the caller, so killing a child killed whoever called `delegate/3`. Whether the kill landed before or after the call returned decided the outcome, which is why the same commit could go either way. Fixed at `1f33f12`, after which both runs of the same commit passed. **What this changes:** "the same commit passed on its other run" is evidence that the failure is *timing-dependent*, which is not the same as evidence that it is environmental. A real race in library code produces exactly the signature R26 is recognised by, so the signature alone cannot be the diagnosis - the stack trace has to be read before a failure is filed here.
